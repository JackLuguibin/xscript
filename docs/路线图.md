# 路线图（策划稿）

这份文档把还没做的功能整理成分阶段的计划，供决定下一步做什么。功能现状的逐项对照见 [功能对照.md](功能对照.md)。如果要按 SaaS 和规模化方向走，整体架构和商业设计见 [商业化设计.md](商业化设计.md)，它会改变这里部分功能的做法（比如设备日志、打包机、签名密钥都要按多租户来设计）。

工作量是粗略估计：**小** 约 1–2 天，**中** 约 3–5 天，**大** 一周以上。实际以开始做之后的拆分为准。

在每张表的「决定」一列填 **做 / 不做 / 以后**，我按这个顺序开工。

## 阶段 0：真机验证（建议最先做）

最近几轮加的功能都只在模拟设备和单元测试上验证过。上线前需要接一台手机或模拟器完整走一遍，发现问题先修。这一步不加新功能，但风险最高。

| 验证项 | 要确认的事 |
| --- | --- |
| 云控连接新后台 | 设备上线、分组、批量启动 / 停止、截图 |
| 远程操控、屏幕墙 | 画面刷新、点击和滑动坐标准确 |
| 运行日志、崩溃上报 | 日志实时显示；脚本报错后后台出现崩溃记录和告警 |
| 卡密 | 激活、6 小时复核、停用后失效、解绑换机 |
| 打包 | 带卡密 / 云控 / 热更新 / 代码保护的 APK 能安装运行 |
| 热更新 | 发布新版本后 App 自动更新；发布旧版本能回滚 |
| 小程序下发 | 定时下发和手动下发都能安装并启动 |

需要准备：一台 Android 手机或 MuMu 模拟器，以及一个手机能访问到的后台地址（同一局域网，或模拟器用 `adb reverse`）。

## 阶段 3：AI 能力

目标：图色和 OCR 认不出来时有兜底手段，并逐步做到「一句话完成任务」。

| 功能 | 价值 | 范围 | 验收 | 工作量 | 决定 |
| --- | --- | --- | --- | --- | --- |
| AI 识屏（VLM） | 没有模板图、界面经常改版时也能定位元素、读数据 | `screen.ai_find("红色的关闭按钮")` 返回坐标；`screen.ai_ask("当前是不是登录页")` 返回答案。接任意 OpenAI 兼容的视觉模型（通义千问、GPT-4o 等），密钥在后台或脚本里配置 | 用自然语言描述能找到按钮并点击 | 中 | ✅ 已完成 |
| AI 智能体 | 给一个目标，模型自己看屏幕、点、输入，直到完成 | 循环：截图 → 模型决定下一步动作 → 执行 → 再截图；可设最大步数和费用上限；每一步记日志 | 「打开设置，把亮度调到最低」能自动完成 | 中到大 | ✅ 已完成（`agent.run`：动作白名单、步数 / 超时 / 停止，每步一次请求即费用上限；模拟服务测试与 arm64 模拟器验证） |
| 后台 AI 写脚本 | 在管理后台描述需求，生成脚本，直接下发到设备测试 | 后台接大模型，结合 API 文档生成代码，一键保存为小程序版本 | 描述一个简单任务能生成可运行的脚本 | 中 | ✅ 已完成（复用 `XSCRIPT_AI_*` 模型配置，密钥只在环境变量；带 API 目录生成 / 修改 `__init__.py`、语法检查、保存为小程序版本；控制台「AI 写脚本」页：写新脚本或载入版本修改、可编辑代码、撤销、保存为版本后一键「下发到设备测试」，小程序版本列表可跳转修改，系统设置有模型配置。用本地模拟模型服务测试，没有接真实模型验证生成质量） |

AI 识屏是后两项的基础，建议先做。模型调用费用由使用者自己的 API 密钥承担。

## 阶段 5：部署与安全

目标：让别人能顺利把后台部署到自己的服务器上，并且更安全。

| 功能 | 价值 | 范围 | 验收 | 工作量 | 决定 |
| --- | --- | --- | --- | --- | --- |
| Docker 部署 | 一条命令起后台，不用手动装 Python 和 Node | `Dockerfile` + `docker-compose.yml`（后台 + Caddy 自动 HTTPS）；数据目录挂载到宿主机 | 新服务器上 `docker compose up -d` 后能访问后台 | 小 | ✅ 已完成（slim / full 两种镜像，见 [部署.md](部署.md)；尚未在真实服务器上构建验证） |
| 打包机分离 | 打包要 Android SDK 和大量内存，和后台放在一起会抢资源 | 打包任务交给单独的打包机执行（后台只排队、分发任务和收 APK） | 后台和打包机在两台机器上也能完成打包 | 中 | ✅ 已完成：`XSCRIPT_PACK_MODE=remote` + `python -m xscript_server pack-worker`（默认仍在本机打包）；打包机令牌认证，领取 / 心跳 / 结果上传协议，日志实时回传、取消、90 秒租约失联重排；测试包括真实 worker 进程端到端（成功、失败、取消、杀掉 worker 后转给另一台） |
| 管理员两步验证 | 后台被盗号的后果很严重（能控制所有设备） | TOTP（Google Authenticator 等），管理员可强制要求开启 | 开启后登录需要输入动态码 | 小 | ✅ 已完成 |
| 登录 IP 白名单 | 只允许公司网络访问后台 | 按角色设置允许的 IP 段 | 白名单外的 IP 无法登录 | 小 | ✅ 已完成（系统设置 → 安全，整站统一名单，不按角色区分；`reset-allowlist` 救援命令） |
| 设备日志持久化 | 现在运行日志只能实时看，设备离线后看不到 | 设备日志写入后台，按设备、时间、关键词检索，按保留天数清理 | 设备离线后仍能查到过去 7 天的日志 | 中 | ✅ 已完成（运行日志 →「历史」，支持搜索、筛选、翻页、导出） |

## 以后再说

这些工作量大、依赖硬件或 GPU，或者需求不明确。等有具体场景时再评估。

| 功能 | 原因 |
| --- | --- |
| HID 硬件（ESP32 / PC 虚拟鼠标） | 需要硬件和驱动 |
| 自带输入法（IME） | 无障碍输入已能满足大多数场景 |
| YOLO 云训练 | 需要 GPU 服务器；本地用 Ultralytics 训练已经可行 |
| 插件市场、应用商店 | 需要有一批第三方开发者才有意义 |
| iOS、Windows 客户端 | 另一套客户端，工作量很大 |

## 建议的执行顺序

1. **阶段 0 真机验证**：先确认已有功能可用。
2. **阶段 1 全部** + **阶段 5 的 Docker 部署**：都是小功能，做完后兼容性和部署体验都有明显提升。
3. **阶段 3 的 AI 识屏** 和 **阶段 2 的网页 IDE**：用户感知最强的两个新能力。
4. **阶段 4**：按你的售卖方式挑选，建议先做「更多卡密类型」「续费」「APK 强制更新」。
5. 其余按需要排期。
