# 发布流程

一次发布同时给出 **App（APK）** 和 **VS Code 插件（vsix）**，用同一个版本号、同一个 Git 标签、同一个 GitHub Release 页面。流程由 GitHub Actions（`.github/workflows/ci.yml`、`release.yml`）执行，`scripts/release.sh` 固化每一步，本机也能重跑。

## 版本号策略

- 版本号 `X.Y.Z`；Git 标签 `vX.Y.Z`；`android/app/build.gradle.kts` 的 `versionName`；`ide/vscode-extension/package.json` 的 `version` 四处一致；手机运行时 `android/python-runtime/xscript/__init__.py` 的 `__version__`（设备 `/status` 上报的版本，模拟设备和演示后端也读它）及 IDE 存根同步，由 `release.sh prepare` 一并修改，`release.sh check` 与 `scripts/tests/test_versions.py` 检查不一致。`versionCode` 每次发布加 1。
- **插件版本 = App 发布版本**。这样 `xscript-vscode-0.2.5.vsix` 一定来自 Release v0.2.5，用户不用对照两套版本号。两者的版本号在发布之间不单独增长（没有发布就没有新版本号）。
- 一致性由 `scripts/release.sh check` 检查，`scripts/verify.sh` 会跑它，不一致就失败。
- 插件不上架 VS Code 应用市场，只放在 GitHub Release（`code --install-extension xscript-vscode-X.Y.Z.vsix`）。以后要上架，用同一个 vsix 和 `vsce publish`，版本号规则不变。
- v0.2.4 及更早的 Release 没有 vsix；从下一个发布起每个 Release 都附带。
- PyCharm 插件同样跟 App 同版本（`ide/pycharm-plugin/gradle.properties` 的 `pluginVersion`，`release.sh check` / `prepare` 一起检查和升级）。release 工作流直接用 verify（ci.yml）里已测试并通过 Plugin Verifier 的 `xscript-pycharm-X.Y.Z.zip`，写进 `SHA256SUMS` 并附到 Release；不上架 JetBrains Marketplace。v0.4.0 及更早的 Release 没有它。

## 步骤（CI 发布，主流程）

推 tag 之后全部由 GitHub Actions 完成：重新跑一遍 CI、构建签名 APK 和 vsix、校验、创建 Release。本机只需要升版本、提交、推送。

```bash
# 0. 在 main 上，verify.sh 全绿；CHANGELOG.md 的「未发布」里是这次要发的内容
bash scripts/verify.sh

# 1. 升版本：改 versionName / versionCode、插件版本（含 package-lock）、README 里的下载链接，
#    并把 CHANGELOG 的「未发布」改成「vX.Y.Z（日期）」。只改文件，不提交
bash scripts/release.sh prepare 0.2.5
git diff                                   # 检查
git commit -am "chore(release): v0.2.5" && git push

# 2. 等 main 上的 CI（.github/workflows/ci.yml）变绿
gh run list --branch main --limit 1
gh run watch

# 3. 打带注释的 tag 并推送，release.yml 接手
git tag -a v0.2.5 -m "XScript v0.2.5" && git push origin v0.2.5
gh run watch                               # release 这条 workflow
```

`release.yml` 依次做：

1. 重新跑 `ci.yml`（`workflow_call`）；
2. 检查 tag == `versionName` == 插件版本、CHANGELOG 有 `## vX.Y.Z（日期）` 小节、tag 指向的提交在 main 上、同名 Release 还不存在；
3. 检查 4 个仓库 Secret 都在，缺任何一个直接失败，**不会**发布未签名或 debug 签名的 APK；
4. 用 Secret 在 runner 临时目录写签名文件（不进工作区、不打印、结束即删），`scripts/release.sh build`：两个签名 APK、vsix、`SHA256SUMS`。两个 APK 是：
   - `xscript-vX.Y.Z-release.apk`：通用包，含 arm64-v8a 和 x86_64，PC 上的安卓模拟器也能装；
   - `xscript-vX.Y.Z-release-arm64-v8a.apk`：只含 arm64-v8a，给手机用，体积约为通用包的一半；
5. `scripts/release.sh verify-apk`（两个 APK 都校验）：签名有效、签名证书 SHA-256 等于已知发布证书、`versionName` 等于 tag、`check_16kb.py` 通过；
6. `gh release create`：说明取自 CHANGELOG 小节，附两个 APK、vsix、PyCharm 插件 zip、桌面端安装包和 `SHA256SUMS`。只有这一个 job 有 `contents: write`。

### 仓库 Secret（只列名字）

| 名字 | 内容 |
| --- | --- |
| `RELEASE_KEYSTORE_BASE64` | 发布签名库（`keys/xscript-release.p12`）的 base64（`base64 < keys/xscript-release.p12 \| tr -d '\n'`） |
| `RELEASE_STORE_PASSWORD` | 对应 `keys/release.properties` 的 `storePassword` |
| `RELEASE_KEY_ALIAS` | `keyAlias` |
| `RELEASE_KEY_PASSWORD` | `keyPassword` |

设置方式：`prop() { sed -n "s/^$1=//p" keys/release.properties | head -1 | tr -d '\r\n'; }`，然后 `prop storePassword | gh secret set RELEASE_STORE_PASSWORD`（值走管道，不要 echo 到终端）。已知发布证书 SHA-256：`e04b22c87fb67b47f1651f078f6e0640f30a555d63d59fbe8d2b86eb504829ac`（`scripts/release.sh` 里的 `KNOWN_CERT_SHA256`）；换签名密钥时同时改这里，并注意已安装的 App 无法覆盖升级。

### CI 覆盖什么、不覆盖什么

`ci.yml`（push / PR 到 main，以及被 release 调用）：

- 管理后台 + MCP 测试，Python 3.10 和 3.12；3.12 上还有 `gen_stubs.py --check`、`gen_completions.py --check`、`gen_editor_docs.py --check`、mock 设备纵向冒烟；
- 设备端 Python 运行时测试（3.10，numpy / OpenCV / Pillow / onnxruntime）；
- Web IDE 的 node 测试（无头 Chrome，ubuntu 自带）；
- VS Code 扩展：编译、单元测试、`vsce package`；
- 管理后台 Web 控制台类型检查 + 构建；
- Android（两个并行作业）：Kotlin JVM 单元测试 + debug APK；未签名 R8 release APK（通用包和 arm64-v8a 包）构建；两边都跑 `check_16kb.py`；
- `release.sh check`（App 与插件版本一致）。

PR 上按改动范围跳过重的作业（`scripts/ci_changes.py`）：所有改动都在不影响 Android 的目录（`desktop/`、`ide/`、`backend/`、`docs/`、`deploy/`、根目录的 README / CHANGELOG 等）时跳过 Android；都在不影响桌面端的目录（`android/` 中除 `python-runtime/` 以外、`backend/`、`ide/vscode-extension/`、`ide/mcp-server/`、`deploy/` 等）时跳过桌面端两个作业。改到 `.github/`、`scripts/` 或任何没列出的地方都照常全跑；push 到 main 和发布时调用的 CI 始终全跑。`ci ok` 作业汇总所有结果，被跳过不算失败，任何作业失败或被取消则它失败。

**不覆盖**（需要设备 / 模拟器或 Mac 工具链）：`scripts/device_*_e2e.py`、`device_screen_smoke.py`、`emulator_grant_capture.sh`；在真实 VS Code 里的扩展宿主测试（`vscode-host-test.sh`，需要桌面和 `/tmp/vscode-real`）；4 KB / 16 KB 页面模拟器上的真机运行；仪器化 Android 测试；`verify.sh` 里的 `.venv310`（CI 的矩阵直接跑 3.10）。发布后建议在模拟器上装 APK 跑一遍 `/status`（版本号）和 `scripts/device_native_e2e.py`。

### 测试设备用的 perf 包（不发布）

在 Actions 里手动运行 `release` 工作流，并勾选 `perf_apk`：
- 只构建开发者 App 的 `com.xscript.app.perf` 版本（`-Pxscript.appIdSuffix=.perf`），可与正式版 `com.xscript.app` 并存安装；
- 用上面的仓库 Secret 签名，并校验签名证书、包名和 16 KB；
- 结果作为 artifact `perf-apk` 上传，保留 1 天；
- 不构建 dmg，不打 tag，不创建 Release，该 job 只有只读权限。

```bash
gh workflow run release.yml --ref main -f perf_apk=true
gh run download <run-id> -n perf-apk -D /tmp/perf-apk
```

覆盖安装（`adb install -r`）要求新包的签名证书与设备上已装的 `com.xscript.app.perf` 一致。不一致时 Android 会拒绝更新，只能卸载重装，而卸载会清掉数据。

本地构建同理：`XSCRIPT_GRADLE_TASK=:app:assembleRelease bash android/build.sh -Pxscript.appIdSuffix=.perf`。

## 步骤（本地兜底）

CI 不可用时才用。`release.sh build` 在本机构建，`release.sh publish` 在本机创建标签和 Release：

```bash
bash scripts/release.sh build              # 签名 APK 需要 keys/release.properties；只要 vsix：加 --skip-apk
bash scripts/release.sh publish            # dry run
bash scripts/release.sh publish --yes      # 要求工作区干净、HEAD == origin/main、标签不存在、SHA256SUMS 与文件一致
```

## 用户怎么校验

```bash
shasum -a 256 -c SHA256SUMS --ignore-missing    # 下载了哪个文件就校验哪个
```
